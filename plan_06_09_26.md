## 1. Правило приёмки слайса — без изменений

Слайс принимается, только если выполняется хотя бы одно:

- **(а)** изменилось наблюдаемое поведение `/api/ask` или UI, и это доказывает E2E-тест;
- **(б)** выросло число реальных размеченных кейсов;
- **(в)** изменилось опубликованное число качества с провенансом (corpus SHA + code SHA + config).

Уточнение для потока GR: «граф построен», «lane написан», «схема таблиц готова» — подготовка. Слайс GR закрывается только числом (в) или E2E (а).

## 2. Центральный тезис плана: precision двигает только ретривер

1. В харнессе фазы C генератор получает **кэшированные** контексты, а `context_precision` и `context_recall` считаются по ключевым словам над этими контекстами. Генератор в них не участвует. Поэтому C.1b (`qwen3:8b`) при любом исходе даст ровно 0.5067 precision, и гейт фазы C «precision ≥ 0.63» **недостижим сменой модели**. C.1b нужен только для faithfulness/latency/RAM (C.4).
2. Recall 0.905 при precision 0.507: нужные чанки находятся, но топ-5 наполовину шум. Это тот же диагноз, что у Yandex Crowd («retrieval попадает в смысл, а не в шаг потока»), и та же дыра, которую в июне не закрыли ни parent-expansion, ни factcard-lane (NO-SHIP 15.06: Δ FULL −18).
3. Следствие: единственный незаблокированный рычаг под правило (в) — ретривер. Графовый поиск в этом плане определяется как **слой сужения и маршрутизации** поверх hybrid, а не как «третий список кандидатов»: аддитивный список поднимает recall, который и так 0.905, и не лечит precision.
4. Числа GR публикуются любыми. «Precision не выросла» — тоже результат под (в), как NO-SHIP factcard.

## 4. Графовый поиск — что строим и чего не строим

**Термины (фиксируются, чтобы доки не путали три разные вещи).**
- *Структурный граф* — документ → секция (heading path) → чанк, плюс рёбра `next`, `same_section`, `cross_ref` (явные ссылки «см. …», «Приказ № …», «п. X.Y …», имя файла), `category`. 0 LLM-вызовов, строится при ингесте из метаданных.
- *Сущностный граф* — узлы `entity` (промпт и парсер `scripts/graph_probe.py`, валидированы 06.06: 200 чанков, 0 фейлов), рёбра `mentions(chunk→entity)`, `co_occurs(entity↔entity, weight)`; в индекс идут сущности из ≥ 2 документов (в probe: awb 60 док., booking 37, hawb 36, mawb 32 …).
- *GraphRAG-framework* (MS GraphRAG, LightRAG, community summaries, Neo4j) — **остаётся замороженным**. Триггер по ADR 0001: > 50 000 чанков на тенант, или доказанный в GR-3 провал на классе `global`, который два первых слоя не закрывают.

**Форма.** Один поток GR из пяти шагов, cheap-first, как предписывает ADR 0001 §3: GR-0 подготовка → GR-1 структурный граф → GR-2 сущностный граф → GR-3 A/B и решение о дефолте → GR-4 продуктовая проводка. Каждый шаг закрывается числом или E2E.

**Хранение.** Таблицы `kb_graph_nodes` / `kb_graph_edges` в Postgres (tenant-scoped, RLS как у остальных tenant-таблиц; миграция 032) — authority по ADR 0003. In-memory проекция `networkx` на тенант, перестраиваемая из таблиц (как Chroma — перестраиваемая проекция). Манифест графа: corpus SHA + версия билдера + версия промпта + digest модели экстракции + счётчики — по образцу `vectordb/index_manifest.py`. Кэш экстракции — `reports/kb_graph/<corpus_sha>/entities.jsonl`, инкрементально по `DocumentChangeTracker`.

**Где в коде.** Lane живёт внутри retrieve-ноды (`agent/graph.py:1430` уже маршрутизирует `graph` → `retriever.get_graph_documents`) и в `HybridRetriever` (`vectordb/_base_manager.py:417`; `_rrf_merge_multiple` есть на строке 1057). Политика и side effects не затрагиваются — ADR 0005 соблюдён. Флаги: `RAG_RETRIEVAL_STRATEGY=graph` + `RAG_GRAPH_RETRIEVAL=on|auto`; оба дефолта — off; при off поведение байт-в-байт прежнее (характеризационный тест).

**Как lane использует граф (это и есть «сужение, не добавление»).**
1. Pre-filter до ANN: `categories`/journey → `where` в Chroma и маска BM25, вместо пост-фильтра.
2. Hybrid-кандидаты как сейчас (`retrieval_k=20`).
3. Section coherence: группировка кандидатов по секции/документу; чанки из секций, уже представленных в топе, поднимаются; одиночные семантические соседи ниже порога отбрасываются.
4. Parent-expansion по границам секции, а не окном ±1.
5. Для `question_class ∈ {multi_hop, aggregation, global}` (из SGR-классификатора GR-0.4): entity-match запроса → соседство 1–2 hop (≤ 50 чанков по весу) → третий список в RRF → общий реранкер → снова п.3. Для `single_hop` — только п.1–4.

**Отклонение от ADR 0001 и как оно оформляется.** ADR говорит «не реализовывать извлечение графа руками — брать LightRAG/nano-graphrag». На 5 589 чанках интеграция фреймворка (своё хранилище, свои вызовы эмбеддера, свои режимы поиска, изоляция тенантов, ещё одна зависимость под security-scan) дороже, чем промпт + парсер, которые уже есть и валидированы. Community detection и summaries не нужны для local-search. Оформляется **постскриптумом к ADR 0001** после GR-3 с числами; ADR не переписывается.

**Чего граф не делает.** Не создаёт данных для фазы B: сущности `awb/hawb/mawb` в корпусе — это регламенты об идентификаторах вообще, а не конкретные отправления; Q2(b) остаётся единственным способом разблокировать B.2/B.3/B.5. Не заменяет hybrid. Не становится дефолтом без GR-3.
