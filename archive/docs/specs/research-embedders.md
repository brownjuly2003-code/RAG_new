## 0. Коротко

- **Основной кандидат — `ai-sage/Giga-Embeddings-instruct-480M-0826` @`1763d60`.** Это единственная модель ≤ 2 GB, которая в ruMTEB v1.1 retrieval выше `bge-m3`: 0.762 против 0.752 в среднем по трём задачам [S3]. На EN-retrieval она тоже выше: 0.570 против 0.510 [S3]. Лицензия MIT, fp32 ≈ 1.93 GB, по стоимости кодирования ≈ как bge-m3 [оц.]. Цена: `trust_remote_code`, обязательная инструкция в запросе, transformers ≥ 4.51, модели 7 недель.
- **Запасной — `ai-forever/FRIDA` @`850455b`, только как «пробник потолка».** Работает без remote code и, вероятно, в текущем venv [оц.]: 0.764 [S3]. Но fp32 весит 3.29 GB, а кодирование ≈ в 2 раза дольше [оц.]. Поэтому он годится только для офлайн-стадии H9, не для рантайма на Mac. Если выиграет, продуктовое продолжение — его дистиллят `sergeyzh/BERTA` (0.51 GB, 0.738).
- **Не пробовать:**
  - Qwen3-Embedding-0.6B: RU 0.676.
  - EmbeddingGemma: −0.037 по RU, gated, стек ≥ 4.56.
  - jina v3/v5: CC-BY-NC.
  - nomic v2 MoE, gte-multilingual, arctic-m: remote code при более слабом RU.
  - e5-base/small, granite, USER2, RoSBERTa, LaBSE-ru-turbo.
  - Модели 2026 года: harrier, pplx, Octen, voyage-4-nano, LFM2.5, KaLM v2.5.
  - Giga 3B.
  - USER-bge-m3, arctic-l-v2, e5-large — «не сейчас»: цена та же, выигрыша нет.
- **Главный риск — тихая деградация.** Код не передаёт промпт и ревизию. У части моделей срабатывает `default_prompt_name`. Модель той же размерности 1024 проходит защиту Chroma и смешивает векторные пространства.
- **Второй риск — рычаг слабый.** Эмбеддер меняет только состав пула. Реранкер пересортировывает весь пул, а потолок пула почти равен потолку текущего top-5 (§3). Ожидаемый исход H9 — NO_SHIP, который закрывает G2.

**Что пересобирать при смене модели:**

- Chroma-коллекции: основную и тенантские (`api/routers/admin_kb.py:426`).
- `chunks.npz` в harness.
- Проекцию знаний — её манифест сам потребует пересборки.

- `scripts/pgvector_spike_db.py:50` содержит захардкоженный `vector(1024)`. Это спайк, но FRIDA (1536) и BERTA (768) его сломают.

Не меняются BM25, чанки и их text hash, реранкер и expansion.

**Ресурсы bge-m3:**

- **Веса** — fp32 2.27 GB, только `pytorch_model.bin` [S1, S9].
- **Процесс** ≈ 3.3 GB [оц.]: веса плюс ≈ 1.0 GB накладных. Калибровка по NLI-процессу: пиковый RSS 2.11 GB при весах 1.12 GB (`docs/evidence/c1b-qwen3-generator-benchmark.md:54`).
- **С реранкером** (ещё 2.27 GB) ≈ 5.5 GB [оц.].
- **Вместе с Ollama** (RSS 5.94 GB, там же) ≈ 11.5 GB > 8 GiB. Поэтому стадии разделены, а перед эмбеддингами выполняется `ollama stop`.
- **Индекс** — 5589 × 1024 × 4 B ≈ 22.9 MB векторов [расч.]; не ограничение.

**Замер на Mac** (стадийный, не бенчмарк):

- G1 pools шёл 6779 с с записью `chunks.npz`, G2 pools из кэша — 80 с.
- Значит, кодирование заняло ≈ 6699 с на 5589 чанков и 100 запросов: ≈ 1.2 с/чанк, ≈ 147 ток./с на MPS при batch 8 [расч.].
- Реранк: 4997 с на G1, ≈ 0.6 с на пару; пул из 34 кандидатов стоит ≈ 21 с/кейс [оц.].
- Источник: `gr2-entity-graph-lane.md:185–215`.

**Стек Mac ML-venv:** Python 3.11.15, torch 2.2.2, transformers 4.44.2, sentence-transformers 2.7.0.

- torch 2.2.2 — последняя x86_64 macOS-сборка torch на PyPI [S12].
- transformers ≥ 4.52 при torch < 2.6 отказывается грузить `.bin` (`check_torch_load_is_safe`, CVE-2025-32434) [S11]. У bge-m3 есть только `.bin`, а реранкер лежит в safetensors [S9].
- Qwen3 появился в transformers 4.51.0. Значит, 4.51.3 — единственная ветка, где Qwen3 и `.bin` уживаются.
- transformers 5.x требует torch ≥ 2.5 [S11], а такого torch для Intel Mac через pip нет.
- Возможности sentence-transformers по версиям [S13]:

  | С версии | Что появилось |

  | 2.4.0 | `prompts`/`prompt_name` |
  | 3.0.0 | `model_kwargs` |
  | 3.2.0 | ONNX/OpenVINO backend |
  | 5.0.0 | `encode_query`/`encode_document` |

**Корпус и запросы** [расч.]:

- 201 файл, 5589 чанков. Длина в символах: p50 648, p90 903, max 973. Контекстный заголовок занимает 20.9 % символов.
- Длина в токенах по 10 токенизаторам кандидатов: max 319–421, p99 265–378. Длиннее 512 токенов — 0 чанков. Значит, max_seq не ограничивает ни одного кандидата (у всех ≥ 512).
- Латиница — 28.6 % букв.
  - Чанки: 3744 русских (67 %), 1672 смешанных (30 %), 173 английских (3.1 %; это в основном списки ссылок и front-matter).
  - Файлы: 139 русских, 62 смешанных, 0 английских.

- **Вывод:** «cross-lingual» у нас — это русский текст с английскими терминами, а не английские документы. Belebele RU→EN (русский вопрос → английский пассаж) — лишь косвенный индикатор.

## 3. Может ли эмбеддер быть главным рычагом precision

Коротко: на текущем конвейере — скорее нет.

1. **Эмбеддер влияет только на состав пула.**
   - Пул — объединение BM25 top-20 и dense top-20 без усечения после RRF. Размер: min 23, медиана 35, среднее 34.27, max 40. В среднем ≈ 14.3 кандидата на кейс приносит только dense-список [расч., пул `91ce1745…`].
   - `_rerank` оценивает весь пул, сортирует и берёт top-5 (`_base_manager.py:828–849`). Порядок RRF на итог не влияет; он важен только в фолбэке при ошибке реранкера.
   - Смена эмбеддера — это смена ≤ 20 кандидатов из 34.
2. **Пул почти не ограничивает качество.** Лексическая прокси — чанк, содержащий все `kws` кейса [расч.]:

   | Где есть такой чанк | Кейсов из 100 |
   |---|---|
   | в пуле | 93 |
   | в реранкнутом top-5 | 84 |
   | в RRF top-5 | 77 |
   | в top-1 | 65 |

   - Между пулом и top-5 теряются 9 кейсов — это потеря селекции, а не recall.
   - Из 7 кейсов без такого чанка в пуле у 2 его нет во всём корпусе. Эмбеддер может достать не больше 5 кейсов.
   - Если каждый такой кейс получит +1 чанк в top-5 (≈ +0.2…0.3 precision), выйдет ≈ +0.01…0.015 в среднем [оц.].
   - Даже при невозможном идеале (5 кейсов с 0 до 1) выйдет +0.05 — ровно порог.
3. **Потолок это подтверждает.** Разведка `.tmp/precision-anatomy-20260923/` (не evidence) на официальной лексической линейке:

   | Что | Значение |
   |---|---|
   | потолок «лучший документ в top-5» | 0.683 |
   | он же в пуле | 0.696 |
   | adaptive-k oracle | 0.6505 |
   | baseline GR-0.3 (без expansion, top-5) | 0.5067 / 0.9050 |
   | P1b с expansion | 0.5768 / 0.9800 |

   Разрыв 0.51 → 0.68 лежит в селекции и гранулярности, а потолок пула добавляет лишь 0.013. Coverage с expansion уже 0.98: запаса на +0.05 там нет.
4. **Аналог — GR-2.** Лента, тоже менявшая только пул, изменила результат в 6 кейсах из 100 и дала +0.0012 (0.5475 → 0.5487, EVIDENCE_INDEX). У эмбеддера поле воздействия шире (до 20 кандидатов на кейс), но механизм тот же.
5. **Классы вопросов.**
   - Фаза C — 99 из 100 кейсов single_hop. Выигрыш от второго доказательного чанка (multi-hop) на этом наборе почти не измерим.
   - Классы, где dense реально нужен: перефразы без лексического пересечения и термины RU↔Latin (AWB ↔ «авианакладная»). Их подгруппа — 38 кейсов со смешанными ключевыми чанками и 29 запросов с латиницей. Её стоит зарегистрировать как разведочную.
   - Номера, коды и точные термины BM25 уже закрывает.
6. **Когда эмбеддер становится главным рычагом.** Если реранкер выключат или урежут бюджет пула ради задержки: на Mac реранк стоит ≈ 21 с/кейс [оц.]. Тогда качество первой стадии идёт в top-5 напрямую. Сейчас это не так, а смена реранкера в стоп-листе плана.
7. **Внешний ориентир.** По статье BGE-M3 на MIRACL-ru сильные модели различаются на единицы nDCG: Dense 70.1, mE5-large 67.4, All 71.7 [S2]. Контролируемого источника о том, какая часть такой разницы переживает cross-encoder реранк, я не нашла (§6).

## 4. Протокол H9 по правилу (c)

H9 — механизм пула. Сравнение идёт на том же корпусе, тех же запросах и
том же бюджете кандидатов (A6 линейки), а не на замороженном пуле.
Вердикты: `SHIP_TO_HOLDOUT` или `NO_SHIP`. Runtime-дефолт при этом не
меняется.

### 4.1 До H9: подготовка (это не слайс)

1. **`get_embeddings`:**
   - параметры `RAG_EMBEDDING_REVISION`, `RAG_EMBEDDING_QUERY_PROMPT`, `RAG_EMBEDDING_DOC_PROMPT`;
   - allowlist моделей для `trust_remote_code` с пином полного sha;
   - промпт всегда передаётся явно, чтобы `default_prompt_name` не подставился молча.
2. **Harness:** те же промпты. В ключ кэша `chunks.npz` добавить ревизию, оба промпта, dtype, max_seq и устройство.
3. **Манифест индекса и Chroma-защита:** хранить и сверять модель, ревизию и хэш промптов, а не только размерность.
4. **Unit-тесты на Windows:** промпт доходит до `encode`; смена ревизии или промпта инвалидирует кэш; подмена той же размерности отвергается.
5. **Отдельный venv на Mac** (`.venv-h9`): torch 2.2.2, transformers 4.51.3; sentence-transformers — текущая 2.7.0, если она совместима, иначе 3.x. `pip freeze` зафиксировать хэшем.

### 4.2 Регистрация (коммит до первого прогона)

- **Руки.**
  - A — `BAAI/bge-m3` @`5617a9f61b028005a4858fdac845db406aefb181`.
  - B — `ai-sage/Giga-Embeddings-instruct-480M-0826` @`1763d603adac8057bd6482a708001b0ed2e0a903`.
  - Обе в fp32 на одном устройстве (mps или cpu, одно на обе), batch 8, L2-нормализация.
  - Промпт B дословно из `config_sentence_transformers.json` модели: запрос — `"Instruct: Given a query, retrieve relevant passages\nQuery: "`, документ — `""`. Доменную инструкцию не подбирать: это тюнинг на dev.
- **FRIDA.** Необязательная третья рука (`search_query: `/`search_document: `), только если её регистрируют сразу. Тогда поправка Холма на две гипотезы. Иначе FRIDA — разведка и вердикта не даёт.
- **Фиксируются:**
  - корпус `c8562a64…e343` (201 файл) и дайджест текстов чанков;
  - набор кейсов и code SHA;
  - реранкер `bge-reranker-v2-m3` @`953dc6f`;
  - `retrieval_top_k` 20, `rrf_k` 60, `rerank_top_k` 5, expansion window 2;
  - lock venv.
- **Первичная метрика — `sent_precision`.** Причина: цель G2 — precision, а у coverage с expansion (0.98) нет места для +0.05. Порог: точечный прирост ≥ +0.05 и нижняя граница CI95 парной разности > 0. Кластерный bootstrap, 10 000 повторов.
- **Non-inferiority (−0.02 по нижней границе CI95):**
  - `evidence_recall_pool` — диагностика самого механизма;
  - `fact_coverage`;
  - кроме того, точечная оценка `all_evidence_coverage` не должна упасть;
  - любая потеря критического факта блокирует, включая PART→MISS.
- **Задержка:** delta p95 retrieve ≤ 200 мс при равном бюджете кандидатов, с поэтапными таймингами.
- **Разведочная подгруппа:** 38 кейсов со смешанными ключевыми чанками и 29 запросов с латиницей. Показывается рядом с основным результатом, вердикта не даёт.
- **D7:** внешние EN-наборы (ConditionalQA, WixQA; MultiHop-RAG — совещательный). Нужны non-inferiority −0.02 и совпадение знака эффекта.

### 4.3 Смена пула и разметка

- **Тексты чанков у рук идентичны:** structural chunking не зависит от эмбеддера. Поэтому единица оценки — ключ «seed chunk id + версия корпуса + SHA-256 текста» — переносится 1:1.
- **Оценки переносятся по text hash.** Вслепую, без метки руки, размечаются только тексты, которые впервые попали в top-5 или в expansion руки B.
- **Показываются два вида результата:** по размеченному и пессимистичный («не оценён = 0», с флагом).
- **BM25-список у рук должен совпадать побайтно.** Это проверка того, что меняется только dense-часть.
- **Harness и `/api/ask` ищут по-разному:** harness — точный cosine по матрице, `/api/ask` — Chroma HNSW. Dev-прогон идёт через harness, holdout — через реальный `/api/ask`.
- **Реранкер** пересчитывает только новые пары. Кэш скоров — по ключу (запрос, text hash, ревизия реранкера).

### 4.4 Паритет и pre-flight (провал = стоп)

1. **Паритет контроля.** В новом venv заново кодируются 200 чанков bge-m3 и сравниваются с архивным `chunks.npz` (`3fcfaf28…`): cos ≥ 0.9999 на всех 200. Иначе контроль целиком перекодируется в новом venv (+≈ 1.9 ч).
2. **Pre-flight B.**
   - Пример из карточки воспроизводится: |Δ sim| ≤ 1e-3.
   - Инструкция реально попадает в токены запроса, у документов префикса нет.
   - dim 1024, норма 1.
   - 20 текстов на CPU и на MPS совпадают с cos ≥ 0.999.
3. **Память.** Пиковый RSS стадии кодирования B не выше, чем у A [оц.: ожидание ≈ 2.9 против ≈ 3.3 GB]. Ollama остановлена.

### 4.5 Мощность и пилот

Формула: n = 7.849 · σ_d² / δ² (α 0.05 двусторонний, мощность 0.8) × DE, где DE = 1 + (m − 1)ρ [расч.].

| σ_d парной разности | n при δ = +0.05 | n для non-inferiority −0.02 |
|---|---|---|
| 0.05 | 8 | 50 |
| 0.10 | 32 | 197 |
| 0.15 | 71 | 442 |
| 0.20 | 126 | 785 |
| 0.30 | 283 | 1767 |

- На 100 кейсах +0.05 различимо при σ_d ≤ 0.178. Non-inferiority −0.02 проходит только при σ_d ≤ 0.071 на вторичных метриках [расч.].
- Если top-5 меняется в немногих кейсах, σ_d мала, но распределение с тяжёлым хвостом. Отсюда bootstrap, а не нормальное приближение.
- **Пилот — 20 dev-кейсов.** Меряет:
  - долю кейсов с изменившимся top-5;
  - σ_d для первичной и NI-метрик (для n берётся верхняя граница 80 % CI);
  - долю неразмеченных новых текстов;
  - паритет и тайминги.
- **После пилота** протокол не меняется, кроме n. Если нужное n больше dev-набора, владелец до полного прогона выбирает: больше кейсов или шире допуск. Выбор записывается в линейку.

|---|---|
| venv, pre-flight, паритет (200 + 20 текстов) | ≈ 0.5 ч |
| кодирование корпуса рукой B | ≈ 1.9 ч (FRIDA ≈ 3.8 ч) |
| перекодирование контроля, если паритет провален | +≈ 1.9 ч |

### 4.7 Когда оставить bge-m3

Достаточно любого из условий:

1. провален pre-flight B или паритет A, и в зарегистрированном стеке это не чинится;
2. пиковый RSS руки B выше, чем у A;
3. после пилота нужное n недостижимо, а набор не расширен. Итог — inconclusive, а не «эквивалентно»;
4. точечный прирост `sent_precision` < +0.05 или нижняя граница CI95 ≤ 0 → `NO_SHIP`;
5. нарушено любое NI, упал `all_evidence_coverage`, потерян критический факт;
6. delta p95 > 200 мс;
7. D7: провалено NI или не совпал знак эффекта.

Опубликованный `NO_SHIP` с полным provenance сам по себе — число по (c): он закрывает G2.

## 6. Рекомендация и неизвестное

Рекомендация:

1. **Сначала подготовка (§4.1)**, потом H9. Подготовка — не слайс: она ничего не меняет по правилам (a), (b), (c). Но без неё результат H9 недоказуем, а подмена эмбеддера в проде опасна.
2. **H9 = Giga-480M против bge-m3**, одна первичная метрика `sent_precision`, пилот на 20 кейсах. Решение принимается по §4.7.
3. **FRIDA — только офлайн-пробник потолка.** Его запускают, если Giga не проходит стек или pre-flight либо владелец хочет оценку потолка. Если FRIDA выиграет, BERTA проходит собственный H9: выигрыш FRIDA на BERTA не переносится.
4. **Порог G5 «≤ 2 GB» пока не принят.** FRIDA его нарушает, Giga (fp32 1.93) укладывается впритык.
5. **Не расширять пул третьей dense-лентой «рядом с bge-m3».** Пул не узкое место (§3). При равном бюджете кандидатов лента вытеснит BM25/dense-кандидатов, а без равного бюджета нарушит правило задержки. Режимы bge-m3 multi-vector/sparse (+1.6 nDCG на MIRACL-ru [S2]) требуют FlagEmbedding и нового хранилища — «не сейчас».
6. **Если пилот покажет, что top-5 меняется в < 10 % кейсов**, а нужное n больше набора, — остановиться. G2 закрывается, bge-m3 остаётся. Рычаг precision — селекция: гранулярность, expansion, правила top-k, а не эмбеддер.

Что осталось неизвестным:

1. Ни одна модель не запускалась на нашем корпусе. Паритет, σ_d, доля изменившихся top-5 и время на Mac не измерены.
2. Cross-lingual (Belebele) у Giga-480M, FRIDA и BERTA: в [S3] результатов нет.
3. EN-качество FRIDA и BERTA (важно для D7): результатов нет.
4. Работает ли remote code Giga на transformers 4.51.3 + torch 2.2.2 + ST 2.7.0 и на MPS: SDPA с двунаправленной маской, bf16 на macOS 13. Модель сохранена на 4.57.0.
5. Совместимость sentence-transformers 2.7.0 с transformers 4.51.3.
6. Память MPS: объём VRAM Radeon Pro 570 и поместится ли FRIDA fp32.
7. Какая часть выигрыша первой стадии переживает cross-encoder реранк. Контролируемого источника не нашла.
8. Пересечение обучающих данных Giga (и FRIDA) с RuBQ, Ria и MIRACL, то есть zero-shot-статус.
9. Совпадают ли веса e5-large с оценённой ревизией: `4dc6d853…` отдаёт 404.
10. RU-результатов нет у voyage-4-nano, LFM2.5 и KaLM v2.5.
11. Совпадение локального дайджеста текстов `cedd1e07…` с `chunk_text_digest` в `chunks.npz` `3fcfaf28…` (Mac недоступен).
12. Есть ли torch новее 2.2.2 для osx-64 через conda-forge — не проверено.
13. Реальный стек и лицензионные условия gated EmbeddingGemma: `config.json` скачать не удалось, прочитана только карточка.
