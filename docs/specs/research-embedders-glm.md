## 0. Коротко

- **Основной кандидат: `deepvk/USER-bge-m3`** `[уверен, что существует; не уверен в деталях карточки]` — дистилляция bge-m3 на русскоязычных данных: та же размерность 1024, тот же ctx, без префиксов → drop-in замена без правок кода из приложения B; на ruMTEB (версия до конца 2024) стабильно **выше** учителя на русском retrieval `[уверен в направлении, не в цифрах]`.

Модели 2025 года (arctic v2.0, Qwen3-Embedding, EmbeddingGemma, granite) — `[не знаю]`, не отсекать, взять у Opus.
- **Главный риск:** эффект плотной ленты размывается связкой BM25 + RRF + `bge-reranker-v2-m3`; доля RU→EN кейсов не измерена — если она < ~10 %, средняя дельта почти наверняка ниже порога +0.05 из линейки D. Сначала посчитать эту долю по sidecar классов (бесплатно), потом переиндексация.

## 1. Как сейчас

- **Класс:** `SentenceTransformer` в обёртке `_STEmbeddings` (`vectordb/_base_manager.py`), LangChain-совместимый интерфейс (`embed_documents`/`embed_query`); выбор через `RAG_EMBEDDING_MODEL`, device — `_resolve_device()` (CPU), глобальный кеш `_cached_embeddings` — одна модель на процесс.
- **Нормализация:** `encode(..., normalize_embeddings=True)` в обоих методах → косинус; remote-бэкенд (`_RemoteEmbeddings`) L2-нормализует идентично, так что бэкенды взаимозаменяемы.
- **Префиксы:** **не добавляются ни для query, ни для passage**. Это критично: смена на модель с обязательными префиксами (`intfloat/*e5*`: `query: `/`passage:`) без патча `embed_query` даст тихую деградацию качества — внедрять такие модели нельзя без правки кода.
- **max_seq_length:** явно не задаётся → модельный дефолт (bge-m3: 8192 `[уверен]`).
- **Размерность:** читается из модели (`get_sentence_embedding_dimension`), у bge-m3 = 1024 `[уверен]`; remote-путь валидирует по `embedding_remote_dimension` (дефолт 1024).
- **Что пересобирать при смене модели:** (1) полный векторный индекс корпуса (пере-эмбеддинг всех чанков; при смене dim — пересоздание коллекции); (2) `RAG_EMBEDDING_REMOTE_DIMENSION` при remote-бэкенде; (3) любые кешированные query-эмбеддинги; (4) патч `_STEmbeddings` — только для префиксных/task-промптовых моделей. BM25, граф, реранкер не трогаются — смена изолирована, что соответствует правилу «один механизм за раз».
- **RAM bge-m3 [оц.]:** 568 млн × 4 байта (fp32) ≈ 2.27 ГБ весов + активации/токенизатор ≈ **2.5–2.9 ГБ RSS**. Реранкер v2-m3 — те же ~568 млн → вместе ≈ 5–5.5 ГБ из 8, впритык до LLM. Метод проверки: `psutil` RSS процесса после `encode()` одного батча. Вывод: замена на модель того же размера не ухудшает бюджет; всё ≥ ~0.6 млрд параметров — уже риск.

## 3. Рычаг precision или нет — честно

- **Каналы влияния эмбеддера** при живом BM25 + RRF + реранкере только два: (1) `evidence_recall_pool` — попал ли gold в пул до реранка (не попал — реранкер не спасёт, бюджет H5 в 40 кандидатов делает это жёстким); (2) порядок после RRF, задающий, кто вообще доедет до реранкера. На top-порядок после реранка dense влияет слабо — перекрёстный энкодер переписывает порядок в пределах пула.
- **Где эффект реален:** RU→EN запросы — единственная лента, матчит через язык (BM25 бессилен, entity-lane по GR-2 сработала на 6/100 и дала +0.0012 — не канал); парафразия/синонимия без общих лексем. **Где эффекта почти нет:** single-hop с совпадающей терминологией (AWB/ULD-лексика закрывается BM25). **Multi-doc:** только через recall пула обязательного второго источника, но GR-2 показал multi-doc unchanged при срабатывании ленты на 11 кейсах — намёк, что bottleneck там selection/coherence, а не coverage; H1 (3.1) для этого дешевле.
- **Baseline 0.5475** — это lexical `context_precision` фазы C (gate 0.63, т.е. разрыв ~0.08). По P2 эта линейка слабо трекает семантику (τ_b 0.156, `RULER_DOES_NOT_TRACK`) — закрывать 0.08 сменой эмбеддера не стоит даже как цели; решение H9 идёт по development-линейке D. Для H9 pre-register: primary `sent_precision` (эмбеддер меняет retrieval), non-inferiority `evidence_recall_pool` ≥ −0.02 (его главный канал) + `fact_coverage`; латентность p95 Δ≤200 мс.
- **Ожидание по величине:** при доле RU→EN и парафраз-кейсов порядка 10–20 % и среднем выигрыше Russian-модели на своём поле средняя дельта `sent_precision` реалистично +0.02…+0.04 — **ниже порога +0.05**; порог достижим, только если CX-подмножество велико или новая модель поднимает recall пула у multi-doc. Поэтому порядок действий: (1) посчитать долю RU→EN и парафраз-классов на dev по sidecar (бесплатно, до любого прогона); (2) зонд USER2-base — дешёвая проверка, что замена вообще что-то двигает; (3) полный A/B USER-bge-m3 против bge-m3 с отдельным CX-срезом; (4) ru-en-RoSBERTa, если CX у USER просел. Все результаты — с corpus SHA + code SHA + model digest по правилу (c); RAG_EMBEDDING_MODEL и векторный индекс — часть конфига капсулы.
- **Конфаундеры:** смена dense меняет вход RRF — прогонять H9 независимо от 3.2 (H5-бюджет) и повторять комбинацию победителей отдельным прогоном; кеш `_cached_embeddings` требует чистого процесса между руками; модели с префиксами — только после патча, и это отдельная строка в code SHA.

### 4.2 Смена пула кандидатов и разметка (чем это решает линейка D)

- Корпус заморожен → тексты чанков идентичны между руками, меняется только отбор. Единица разметки (A4): текст = seed chunk id + corpus_version + SHA-256 текста → оценки P2 переносятся по хешу без переразметки.
- Новые документы: рука B выталкивает в top-5 / sent-context тексты вне скоупа P2 (P2 — unexpanded top-5). По D: документы, которые механизм «newly surfaces», размечаются тем же слепым способом **до** сравнения; объединение (top-5 seeds ∪ sent contexts) обеих рук; неразмеченный документ = 0 только в помеченном пессимистичном виде; решающее сравнение — по полностью размеченным рукам.
- `evidence_recall_pool`, `all_evidence_coverage`, `fact_coverage` считаются по gold-спанам кейса (разметка кейса, не документов): gold-спан матчится по офсетам/нормализованному тексту той же версии корпуса — смена пула ретрива новых оценок не требует.
- Объём [оц.]: 5–15 новых текстов на кейс → 500–1500 на 100 кейсов; при `build_request` v1 (ровно 5 документов) — 100–300 судейских запросов; v2 (1–10, слайс 2.7) сокращает [не знаю, залит ли 2.7 к моменту H9 — проверить в коде].
- Если позже меняется корпус (вне H9): новый corpus SHA, перенос оценок только по совпадению хешей, новые тексты переразмечаются, новые классы вопросов — человеческий подсемпл ≥10 кейсов на класс (A1) до любых заявлений о семантическом выигрыше.

### 4.3 Метрики

- **Primary (GLM-2, до прогона): `sent_precision`** — эмбеддер меняет отбор; итоговую полезность определяет то, что послано генератору, канал покрытия держится NI-сетом.
- Non-inferiority (−0.02, CI95 LB): `evidence_recall_pool` (главный канал эмбеддера), `fact_coverage`; `all_evidence_coverage` — точечная оценка не падает; потеря критического факта на любом регрессионном кейсе блокирует (PART→MISS и потери внутри PART учитываются, FULL/PART/MISS печатаются рядом).
- Рядом, не гейтят: `precision_at_5`, `ndcg_at_5`, `abstention_*`, лексическая `context_precision` фазы C (0.63 печатается, не условие — D6), абсолютные p50/p95 retrieve и по-стадийные тайминги (`pools`, `rerank`, `coherence_expand`).
- Latency-гейт: retrieve p95 Δ ≤ 200 мс при равных бюджетах кандидатов; кандидат равного bge-m3 размера даёт Δ ≈ 0 [расч.].
- Вторичные срезы, регистрируются до результатов, вердикт не меняют: (1) CX-срез — RU-вопрос → EN gold-документ (членство по sidecar + ручная проверка gold-источников до прогона); (2) срез без лексемного пересечения (парафразия). Свои CI; диагностируют канал.

### 4.4 Выборка и мощность

- Пилот: 20 кейсов, стратификация по классам sidecar, все найденные CX-кейсы до 5 шт.; парные разности `sent_precision` на одних кейсах; новые тексты пилота размечаются до подсчёта.
- Полный прогон: 100 кейсов dev, если мощность достигается; иначе — решение владельца «больше кейсов / шире маржа», фиксируется в спеке до старта (GLM-3).
- Арифметика [расч.]: superiority n ≈ 3136·σ_d² (Δ = +0.05, power 0.8, CI95 LB > 0); NI −0.02 при истинной Δ = 0: n ≈ 19 600·σ_d².

| σ_d | n для +0.05 | n для NI −0.02 | MDE при n=100 |
|---|---|---|---|
| 0.15 | ~71 | ~441 | ~0.042 |
| 0.20 | ~125 | ~784 | ~0.056 |
| 0.25 | ~196 | ~1225 | ~0.070 |

### 4.5 Стоимость переиндексации на Mac [оц.]

- Полная переиндексация обязательна под каждую руку-кандидат (ретрив по всему корпусу, частичный индекс невалиден); BM25/граф/реранкер не пересобираются. Индекс контроля существует (фаза C) → платная часть = 1 переиндексация на кандидата + 1 на зонд.
- T ≈ N·t_chunk; из части A: 568M ≈ 5–15 с/чанк (CPU fp32, i5-7500); ~150M-класс в 3–4 раза быстрее [расч.]. Перед прогоном t меряется на 100 чанках и экстраполируется.

| N чанков | 568M (5–15 с) | ~150M (1.5–5 с [расч.]) |
|---|---|---|
| 1 000 | 1.5–4 ч | 0.5–1.5 ч |
| 5 000 | 7–21 ч | 2–7 ч |
| 20 000 | 28–83 ч (ночные сессии, чекпоинты) | 8–28 ч |

- N в приложениях отсутствует — снять из статистики индекса на префлайте (бесплатно) до решения о прогоне.
- Диск: N·dim·4 B ≈ 82 МБ на 20k×1024 — незначимо; индексы рук хранятся раздельно (контроль не перезаписывается), кеш по (model, revision, corpus SHA) делает повторные прогоны бесплатными.
- Память: переиндексация соло-процессом только с эмбеддером (≈2.5–3 ГБ RSS [оц.]); лог tokens/s, чекпоинты каждые ~500 чанков (resume после OOM/сна).
- Query-сторона: 1 текст на кейс, ≤1–2 с [оц.] внутри стадии `pools`; дельта между равными по размеру моделями ≈ 0 → гейт 200 мс не под угрозой; заметно больший кандидат — риск.

### 4.6 Порядок прогона

0. **Бесплатно, до загрузки моделей:** доля CX и парафраз-классов на dev по sidecar. Доля CX < ~10 % → ожидаемая Δ ниже MUE: решение владельца «парковать H9 или гнать зонд» — записать до всего.
1. **Префлай:** pin revision + дайджесты; загрузка в закреплённом окружении (кандидаты с remote code отваливаются здесь); триплет-смоук (5.3); RSS; t_chunk на 100 чанках; N из индекса.
2. **Зонд `deepvk/USER2-base`** (если не припарковано): переиндексация + пилот 20 кейсов, без полного прогона. Правило продолжения [оц.]: зонд не двигает заметно `evidence_recall_pool`/CX-срез даже направленно → тяжёлые руки не запускать, H9 закрыть.
3. **Переиндексация основного кандидата** (ночь), чистый процесс.
4. **Пилот 20 кейсов:** парные прогоны обеих рук (разные процессы — глобальный кеш `_cached_embeddings`), слепая разметка новых текстов, σ_d, прикидка мощности, направление CX-среза. Ранний стоп (правило спеки): точечная Δ < +0.02 и CI95 UB < +0.05 → досрочный NO_SHIP, публикация как inconclusive/отрицательная Δ с provenance.
5. **Решение владельца по мощности** (если нужно) — в спеку, до полного прогона.
6. **Полный прогон** 100 (или расширенных) кейсов: paired bootstrap 10 000, кластеры, вердикт `SHIP_TO_HOLDOUT` / `NO_SHIP`; капсула по provenance-списку D + модельные поля из 4.1.
7. `SHIP_TO_HOLDOUT` → research acceptance 4.1: locked holdout через реальный `/api/ask` на `deproject-mac` (в памяти появляется LLM — 5.1), включая лексическую `context_precision` на H не ниже контроля −0.02, tenant isolation и streaming parity на том же билде.
- Изоляция: H9 не совмещается с 3.2 (бюджет H5) и изменениями графа; комбинация победителей — отдельный прогон (3.7).

### 4.7 Критерий «оставить bge-m3»

Оставить `BAAI/bge-m3` runtime-дефолтом (и закрыть H9), если верно любое из:

1. доля CX + парафраз < ~10 % и владелец не расширяет постановку (шаг 0);
2. префлай кандидата провален: не грузится / лицензия / триплеты / RSS выше бюджета;
3. пилот: Δ < +0.02 при CI95 UB < +0.05;
4. полный прогон не прошёл композит: primary < +0.05 или CI95 LB ≤ 0; любое NI-нарушение; потеря критического факта; p95 Δ > 200 мс;
5. CX-срез просел точечно > 0.05 — эскалация владельцу даже при среднем прохождении (bge-m3 силён именно в RU↔EN [уверен]; RU-дистиллят может отдать EN назад);
6. holdout 4.1 не прошёл.

Смена дефолта — только после `SHIP_RESEARCH` на holdout и product acceptance 4.2 с поименованным SLO (D5); per-tenant флаг — после 4.2. Никакой вердикт сам дефолт не меняет (D).

## 5. Риски

### 5.1 Память (эмбеддер + реранкер + LLM одновременно)

- Бюджет: 8 GiB всего, macOS 13 системно ~1.5–2 ГБ [оц.]; bge-m3 fp32 ≈ 2.3 ГБ весов → 2.5–2.9 ГБ RSS [оц.]; `bge-reranker-v2-m3` — те же ~568M → ~2.5–2.9 ГБ. Пара ≈ 5–5.8 ГБ — текущий дефолт уже на грани; кандидат равного размера бюджет не меняет, всё ≥ ~0.6 млрд параметров — блок. FRIDA ~3.5 ГБ [не уверен] — блок для совместного прогона.
- Генерация (4.1): LLM добавляется к паре; если сейчас тройка помещается — равный кандидат не ухудшает. Пиковый RSS мерить (memory compression macOS искажает наивный RSS [не уверен в деталях]); запасной `ru-en-RoSBERTa` (~1.8 ГБ [оц.]) освобождает ~0.8 ГБ — единственный кандидат, улучшающий бюджет генерационных прогонов.
- Своп = тихая порча латентности: мониторинг memory pressure, стоп-условие прогона; переиндексация только соло-процессом.
- int8/ONNX-квантизация — отдельный слайс (новая зависимость + код), не в H9 [не уверен в зрелости пути под закреплённой парой ST/torch на macOS 13 Intel].

### 5.2 MoE и кастомные архитектуры под sentence-transformers на CPU

- Код вызывает `SentenceTransformer(model_name, device=device)` без `trust_remote_code` → `Alibaba-NLP/gte-multilingual-base`, `jinaai/jina-embeddings-v3`, `nomic-ai/nomic-embed-text-v2-moe` либо не грузятся, либо требуют патча (новый code SHA); поведение зависит от закреплённой версии ST [не уверен в дефолтах — проверить на префлайте].
- Кастомные слои тянут требования к transformers/torch, которых может не быть в окружении Intel-CPU macOS 13; MoE-роутинг добавляет CPU-накладной и точек отказа. Префлай-критерий: «грузится и кодирует в закреплённом окружении без патчей», иначе кандидат отбрасывается как не соответствующий бюджету слайса, а не как «плохая модель».

### 5.3 Префиксы: ошибка = тихая деградация

- Код не добавляет префиксы ни query, ни passage; e5-семейство обязательно требует `query:`/`passage:` [уверен], jina — task-промпты, instruct-модели — инструкцию на query. Внедрение без патча `_STEmbeddings.embed_query` даёт векторы не из той пары распределений — без исключений, качество просто падает.
- Гейты: (a) префикс-контракт в спеке (4.1); (b) триплет-смоук: ~20 RU query→релевантный RU passage, 10 RU→EN релевантный, 10 дистракторов; средняя cos(релевантные) должна доминировать над cos(дистракторы) с запасом ~0.05–0.1 [оц.] — провал = стоп руки; (c) патч префиксов = отдельная строка code SHA и отдельный прогон, не правка по ходу.

### 5.4 Размерность и пересборка индекса

- dim ≠ 1024 → новая коллекция, A/B в одном сторе невозможен; смена dim заодно меняет тюнинг ANN — конфаундер. Ship-кандидаты держать в 1024 (USER-bge-m3); 768 у USER2-base — только зонд.
- Тихий кросс-модельный конфликт: remote-бэкенд `mistral-embed` тоже 1024d [уверен] → валидация `embedding_remote_dimension` **не** ловит запросы одной моделью по индексу другой. Гейт: индекс-манифест (repo + revision + digest весов + dim), query-путь ассертит совпадение с манифестом, тест в CI; в H9 `RAG_EMBEDDING_BACKEND=local` + лог модели на query.
- Сбой посреди переиндексации не должен смешивать старые/новые векторы: пересборка в свежую коллекцию, атомарная замена по манифесту.
- `get_sentence_embedding_dimension` может вернуть `None` на кастомных архитектурах → обёртка оставит dim неопределённым; длину векторов первой партии проверять явно.

### 5.5 Лицензии

- `jinaai/jina-embeddings-v3` — CC-BY-NC-4.0 [уверен]: коммерческий домен поддержки → жёсткий блокер независимо от качества.
- Gemma-термы (embeddinggemma, 2025) — кастомная лицензия с ограничениями [не знаю деталей] → знак юриста/владельца до любого прогона.
- MIT: bge-m3, e5 [уверен]; Apache-2.0: gte [не уверен]; ai-forever (RoSBERTa, FRIDA) и deepvk (USER*) — [не знаю/не уверен]: проверять по карточке в момент пина, лицензия записывается в спеку; NC/custom → блок или явный знак владельца.

### 5.6 Дрейф revision на HF

- `SentenceTransformer("name")` резолвит дефолтную ветку на момент загрузки: апдейт весов/токенизатора между прогонами делает числа невоспроизводимыми; прецеденты замены и изъятия файлов на HF известны [уверен в общем, без ссылок].
- Правила: пин commit SHA; SHA-256 весов в капсулу (D: model digests); локальное зеркало в закреплённом кеше; перепроверка дайджеста перед holdout-прогоном (недели спустя); смена дайджеста = новый слайс.
