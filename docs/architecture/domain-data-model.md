# RAG_new domain and data model

- Status: Proposed implementation baseline
- Last updated: 2026-08-21
- Authority: PostgreSQL for durable state; Chroma for rebuildable retrieval projection

## 1. Aggregate boundaries

The model uses small aggregates instead of one serialized graph state.

| Aggregate | Consistency boundary | Principal invariant |
|---|---|---|
| `ResolutionContractVersion` | One immutable published procedure version | Published content never changes; effective overlap is explicitly resolved. |
| `SupportCase` | One tenant-owned resolution lifecycle | A transition uses the expected case version and a published contract. |
| `EvidenceSnapshot` | One immutable observation/content version | Digest, source, validity, and visibility cannot be rewritten after use. |
| `PolicyDecision` | One deterministic decision record | Result is bound to policy revision and normalized input digest. |
| `ActionRun` | One logical external operation | Tenant/action/idempotency identity is unique; terminal state cannot regress. |
| `PostconditionResult` | One checker execution against observations | Result names checker and input versions; LLM text is not accepted. |
| `ResolutionOutcome` | One terminal assessment for a case version | `verified` exists only when every required gate passes. |
| `ReplayRun` | One immutable release manifest and scenario set | Candidate generation cannot read hidden expected results. |

Cross-aggregate behavior is coordinated by an application service and transaction. External calls occur after an outbox commit and are reconciled back into a new transaction.

## 2. Core identifiers and version rules

- Public durable entities use UUIDs generated by the application; integer sequence IDs may be used only for private append order.
- Every tenant-owned table includes `tenant_id` in unique keys and foreign-key ownership checks.
- Contract IDs are stable slugs; versions use semantic version strings plus an immutable content SHA-256 digest.
- Knowledge and evidence versions use immutable content digests and source version identifiers where available.
- `SupportCase.version` is a monotonically increasing integer used for compare-and-swap.
- Time is stored as timezone-aware UTC. Business validity and system-recorded time are distinct.
- Human-readable reason codes are enums/versioned vocabulary; free text is supplementary and never drives policy.

## 4. Contract representation

Authoring models are strict Pydantic models and export JSON Schema. Unknown fields fail validation. Runtime execution uses the validated canonical JSON payload and does not execute YAML directly.

Minimum sections are:

```yaml
schema_version: resolution-contract/v0.1
id: aircargo.shipment-status
version: 0.1.0
owner: logistics-ops
risk_tier: read_only
effective: {from: 2026-09-01T00:00:00Z, to: null}
eligibility: {}
required_inputs: []
evidence_requirements: []
rules: []
steps: []
postconditions: []
terminal_outcomes: {}
escalation: {}
disclosure: {}
budgets: {}
```

Rules use a closed predicate AST such as `all`, `any`, `not`, `eq`, `in`, `exists`, `lt/lte/gt/gte`, and typed date/range comparisons. Field paths are checked against declared inputs/evidence. No arbitrary functions, regular expressions with unbounded behavior, network access, template execution, or dynamically imported checker names are allowed.

Static validation verifies:

1. IDs, schema and semantic version formats.
2. Reachable terminal state for every branch.
3. Every write step has risk, scope, confirmation, idempotency, timeout, and postcondition declarations.
4. Every evidence requirement names authority, freshness/valid-time, and conflict behavior.
5. Referenced adapters/checkers exist with matching version/schema digests.
6. Budgets are finite and within tenant/risk ceilings.
7. Required disclosure and handoff payloads are defined.
8. No published effective-range collision is left ambiguous.

## 5. Bitemporal knowledge model

`valid_range` answers “when was this true in the business?” and `system_range` answers “when did this system know/store that version?”. A case resolves knowledge at its contract-defined business timestamp and at the replay/runtime system timestamp. Replays can therefore reproduce both the answer that was possible then and the answer current knowledge would produce now.

Suggested logical records:

- `knowledge_objects`: stable tenant/source identity, owner, authority class, visibility and review SLA;
- `knowledge_versions`: immutable content digest/reference, valid/system ranges, locale and source revision;
- `knowledge_applicability`: product, region, customer plan, cargo type, channel or other typed dimensions;
- `knowledge_supersessions`: explicit predecessor/successor relation and reason;
- `knowledge_conflicts`: normalized fact keys, conflicting versions, resolution status and owner.

PostgreSQL `tstzrange` plus GiST indexes support point-in-time eligibility. Exclusion constraints prevent unintended overlap within the same authoritative source and applicability key. Overlap across distinct authorities is allowed so conflicts can be represented, ranked, or escalated instead of silently erased.

Eligibility order is deterministic:

1. tenant and visibility/ACL;
2. applicability dimensions;
3. business-valid time;
4. system-known time for replay;
5. explicit supersession;
6. authority priority and owner status;
7. retrieval among the remaining eligible versions;
8. fact-level conflict and evidence-coverage checks.

Chroma stores projection IDs that resolve back to eligible `knowledge_version_id` values. A projection manifest records source version digests and embedding/index configuration. A missing or stale manifest fails the verified lane; it does not fall back to an unknown collection.

## 6. Evidence ledger semantics

The ledger is append-only at the application boundary. It records inspectable artifacts rather than hidden model reasoning:

- source snapshots or protected references and digests;
- normalized facts and conflict relations;
- model/provider/prompt/index/contract/policy/connector/checker versions;
- action request/result metadata after redaction;
- confirmation and actor identity;
- state transitions and postcondition outcomes;
- trace/correlation identifiers.

Content hashes prove identity and detect accidental mutation; they do not make PostgreSQL cryptographically tamper-proof against a database administrator. If regulated WORM or externally verifiable integrity becomes a requirement, add signed export manifests or an external immutable log via a separate ADR.

Claim support is explicit and many-to-many. A material claim without valid supporting evidence cannot enter a verified response. Contradictions remain visible and trigger the contract's clarify/escalate behavior unless a deterministic authority rule resolves them.

## 7. Action idempotency and outbox

An action idempotency digest is derived from tenant, case, contract step, manifest version, canonical typed input, and logical operation key. Raw user-supplied idempotency values are salted/hashed where exposure is sensitive.

The database enforces one logical `ActionRun` per digest. The transaction that creates the run also appends its outbox event. Workers lease runs with bounded expiry and record attempts. A retry after a crash acquires the same run, not a new one.

States are monotonic:

```text
requested -> awaiting_confirmation -> ready -> leased -> dispatched
          -> succeeded -> postcondition_passed
          -> failed
          -> outcome_unknown -> reconciling -> succeeded|failed|escalated
          -> cancelled|expired
```

`dispatched` is not success. A connector timeout after possible mutation becomes `outcome_unknown`. Reconciliation queries the remote operation or desired state using the persisted remote/idempotency identity. A compensation is a new governed action with its own policy decision and evidence, never an unlogged rollback shortcut.

## 8. Tenant and authorization constraints

All repository methods require a `TenantContext`; no unscoped `get(id)` method exists for tenant data. Composite foreign keys include tenant ownership where practical. PostgreSQL RLS is enabled with default-deny policies, and production uses a runtime role that does not own or bypass protected tables. Migration/maintenance roles are separate and audited.

RLS is defense in depth, not a substitute for API RBAC or resource-level authorization. Evidence export additionally checks purpose/scope, because an actor allowed to view a case may not be allowed to download raw source material or connector payloads.

## 9. PII, encryption, and retention

- Sensitive customer content uses the existing encryption abstraction or a reviewed successor with keys outside the database.
- Logs, spans, metrics, decision logs, replay fixtures, and evidence exports use explicit redaction profiles.
- Raw prompts, connector arguments/results, bearer tokens, credentials, and full documents are not telemetry by default.
- Evidence retention is tenant- and purpose-specific. Deletion propagates to protected payloads and retrieval projections while preserving the minimum lawful audit tombstone/digest when policy permits.
- Replay datasets are de-identified, access-controlled, versioned, and never silently repopulated from production.

## 10. Migration sequence for data

1. Add schema-only contract registry and lifecycle tables.
2. Add case/event/evidence tables and repositories without routing production traffic.
3. Add tenant RLS and cross-tenant negative tests before storing shadow cases.
4. Add one knowledge source's temporal/authority metadata and projection manifest binding.
5. Add policy decisions and read-action manifests.
6. Add action/outbox/postcondition records before wrapping any write connector.
7. Add replay/release tables and retention/backup coverage.

Each Alembic revision has upgrade/downgrade tests on PostgreSQL, model parity checks, restore evidence where data semantics change, and a rollback statement. SQLite may remain a unit-test adapter but cannot close PostgreSQL-specific range, RLS, exclusion, or locking gates.
